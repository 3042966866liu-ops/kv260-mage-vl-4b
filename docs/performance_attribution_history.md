# 一次固定视频请求的耗时在哪里

独立安装的固定视频样例在稳定 Build `0x4D395832` 上首 Token 用时 `230.721 s`，不含初始化。四张 RGB448 帧按顺序提交，但模型只取最后一帧形成两张视图；输入为 159 Token、五个 T32 批次。这是一条**单次直接推理记录**，不是多个请求的延迟分布，也不是持续视频流的更新时间。

| 互斥阶段 | 耗时 | 首 Token 占比 | 计时边界 |
| --- | ---: | ---: | --- |
| 视频预处理 | `0.072 s` | `0.03%` | 取末帧并准备视觉输入；不含浏览器上传 |
| PS 视觉塔 | `43.638 s` | `18.91%` | 24 层视觉前向 |
| Token 构建、语言 Prefill 至受限首 Token | `187.011 s` | `81.06%` | 包含主机侧运算、权重处理、PL 事务、输出头与选择；此记录未再拆分 |
| **合计** | **`230.721 s`** | **`100%`** | 不含初始化；四舍五入差约 `0.00005 s` |

[公开机器摘录](../experiments/fixed_video/RESULT.json)保留输入和输出身份，并指向维护者原始板端记录的 SHA-256。初始化至预处理另有 `149.695 s`；整段测试 runner 为 `511.854 s`，其中还包含校验和收尾，不能作为纯推理时间。

这个分解给出一个直接的工程判断：在当前 159-Token 请求里，语言阶段占主要等待时间。即使视觉塔耗时理想地归零，首 Token 仍约为 187 秒；这只是按已有计时相减的理论下界，并非一个可实现的优化预测。

## 为什么没有继续细分到每一次 DMA

较早的 849-Token 语言-only 画像记录了权重准备、内存复制、寄存器设置、设备等待、输出同步和解析，但它与上述 159-Token 固定视频不是同一输入。部分活动存在预打包/解析并行，嵌套计时也不能求和；设备等待尤其不等于纯 PL 计算。将那个画像按 Token 比例缩放到 `230.721 s` 会制造不存在的精度。

同板 159-Token 边界探针有三次语言段约 `131.5 s`，但它复用了视觉特征，缓存及请求边界与独立安装的视频记录不同。因此本页只使用固定视频的互斥顶层时间；849-Token 画像的来源哈希和关键数字保存在[历史归因摘录](performance_attribution_history.json)，另见[批边界探针](../deployment/mage_vl4b/M294R3_COUNTERBALANCED_BOUNDARY_BOARD_RESULT_05.json)。

## 组件提速为什么没有变成完整请求提速

输出解析候选在 A53 短测中，对三种形状观察到约 `1.76–2.04×` 的局部改善。但两组相反顺序的固定视频 A/B 中，候选首 Token 分别比稳定实现慢 `20.224 s` 和 `7.023 s`。差额均出现在语言 Prefill 顶层；当时没有同请求的权重读取、解析和 PL 等待细项，不能断言解析器使整条路径变慢，也不能把短测收益外推为整模型加速。工程取舍是保留稳定实现，并归档这项负结果。[M332 双顺序结果](../experiments/m332_parser_scale/CLOSURE.json)。

若未来重新定位延迟，最有价值的是在同一输入与同一缓存条件下，将 `187.011 s` 再拆为权重读取/解包、PS 算子、DMA/设备等待、输出解析与采样，并记录插桩开销。当前发布版本没有这些同请求细分数据。
