# M337 授权本地视频的快通道输入诊断

本轮为**离线开发诊断**，不是 KV260 自动报警、4B 复核、连续实时流或检测准确率验收。六段用户提供的约 21 秒、4K/30 FPS 视频仅在本地读取；视频、人物画面和原始帧不随仓库发布。六段均来自近似的厨房、机位和人物，不能拆成相互独立的开发/测试场景。

使用未改 M335 页面 `app.js`（SHA-256 `3aa35208a7739cb9068796735aec78410f39f94d48041f0b41bf3cf397dfd95e`）及其原 `drawCover()`/`sendFrame()`，对六段视频分别在 0.5 秒固定间隔 seek，得到 253 个 RGB448 帧。浏览器计算的帧 SHA-256 与本机 loopback 接收器逐帧一致。这是确定性的 **2 FPS 时间点抽样**，并非按墙钟运行的连续流；没有访问开发板。

用原 M249 SSDLite/COCO checkpoint（SHA-256 `a79551df90c79834bcd3bb3845ef9d966b5449a3a9b2833ae8404778ca5d65d2`）在 WSL CUDA 软件环境评分；原 `0.05` 检测过滤、`safe=0.20`、`alarm=0.80` 保持不变。代表性网页输入中，前三段有清晰可见的菜刀；另两段主要分别为汤勺、剪刀；第六段以清洗/整理食材为主，未完成逐窗口正式标注。

| B：持菜刀切菜 | 42 | 0.068310 | 0 | 0 | 0.101745 |

| E：剪刀 | 42 | 0.087223 | 0 | 0 | 0.112238 |
| F：清洗/整理 | 42 | 0.000000 | 0 | 0 | 0.000000 |

中心放大对照只把同一 RGB448 帧的中心 `[56:392,56:392]` 双线性放大回 448×448；它**不是当前网页的实际输入**。C 有一帧刚达到 0.20，但 D 也有一帧达到 0.20 且峰值更高；A 的清晰菜刀得分反而下降。两种输入均无 0.80 命中。故中心放大没有建立可信的刀具/相似物分离，未接入运行时，也没有为了演示降低阈值。

现有证据排除了“网页完全裁掉刀具”和“浏览器到接收端字节改变”作为这批样本的充分解释，提示原通用检测器对目标场景响应弱；**不能**据此确定具体根因、计算召回率/FAR，或声称 WSL GPU 与 KV260 A53 分数逐位一致。M335 已通过的手动 Web→4B/FPGA→SSE 链路也不等于自动报警链路通过。

复现代码：`scripts/optimization/m337_capture_real_video_rgb448.js`、`m337_score_real_video_rgb448.py`、`m337_zoom_ablation.py`。运行需要私有原视频及与上述 SHA 匹配、按[外部资产清单](../../manifests/external_assets.json)取得的检测器权重；仓库不提供这些视频、权重或预计算原始 RGB 帧。下阶段须先冻结窗口级可见性标签，再用不同场景、人物和机位的正负片作独立盲测。正式自动报警与 4B 复核仍待实板验证。
