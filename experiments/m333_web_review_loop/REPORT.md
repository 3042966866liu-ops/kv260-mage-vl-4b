## Web 链路发现与隔离实现

原 M254 `AlarmOnlySemanticReview` 在首次报警时把 `_review_queued` 设为 `True`，但没有任何完成或失败时清除此状态的代码；已有 M254 离线测试只验证首个复核入队。因此它至多能证明一次性复核，不满足同会话多次新事件的连续复核要求。另一个风险是快速检测结果迟到时，原桥直接取最近四帧，未限定在触发报警的 source sequence 之前。

M333 隔离候选采用“一个运行中任务＋一个最新待处理任务”：

1. `safety_result` 先发布，不等待 4B；同一连续 ALARM 只触发一个复核请求，报警解除后再出现才算新事件。
2. 复核输入从最多 16 张有界 source 帧中按报警 sequence 取对应的前四张；若源帧已不可得则显式跳过，不拿未来帧冒充报警画面。
3. 4B 忙时新事件只覆盖一个最新待处理任务，不生成无界队列；终态只在 semantic 本地 sequence 与当前任务匹配时释放，旧终态不清除新任务。
4. `window_complete`、`window_error` 和提交失败均释放对应任务；提交失败不会杀死快速检测工作线程。终态在提交返回前到达也被暂存并处理。

`m333_video_server.py` 是隔离 Web 入口，复用原 M254 的前置检查与引擎，只在接受第一帧前替换桥接回调并订阅 semantic 事件。**这不是当前板上服务的新版本，也未打包上传。**

## 实际验证边界

`test_m333_review_bridge.py` 用假检测结果、假 semantic sink 和真实 `EventJournal` 做 13 项离线检查，最终全部 PASS：第一次报警的四帧、忙时只保留最新不同事件、成功后继续、失败后恢复、旧终态不误释放、延迟报警不取未来帧、快通道先于慢通道、提交期间提前终态、隔离 Web 回调接线等。`RESULT.json` SHA-256 `ce9bd3c02d369c462b837f93cea84903b2613e15d7ef7f7d3ddfcc20feb49fc8`。首次测试脚本自身把 8 个 `safety_result` 错计为 7，离线 FAIL 后只改断言计数、同级复测 PASS；未触碰稳定实现。

此 PASS 仅证明调度/事件契约，**未验证**实际 HTTP/SSE、真实 M249 检测器、4B 模型前向、FPGA 调用、两次真实 Web 复核或公网访问；不能称完整 Web 链路 PASS。原 M254 板端证据也仅是无帧 runtime-ready，M328 是绕过 Web 的直接四帧 4B 视频推理。

## 下一具体门禁

先对隔离入口做 HTTP/SSE 假运行时集成，核对两次事件的帧与任务身份、成功和失败终态；再做独立白名单/哈希包与板端环境预检。实板按既有 Build-ID→单 descriptor→单 chain→单 layer→固定文本 E2E 历史同身份证据复用后，才用原稳定 Build 做一个可触发报警的固定视频 Web 事务和第二次新事件，要求每次有 fast `safety_result`、semantic `window_begin/complete`、4B proof、FPGA 调用和最终 Web 回传。无报警的快通道结果不能冒充 4B 复核。任何失败仅调试失败层级，保持稳定服务与回滚；板端 PASS/FAIL 必须同步权威 JSON 和状态文档。

BACT 独立质量门禁仍需真实新来源和人工标签，旧 12 段不重复计为新测试；在这之前仅维持已证实的成本结论。
